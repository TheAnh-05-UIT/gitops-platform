# Development roadmap

Use the [observed baseline](PROJECT_STATE.md) and [contracts](ARCHITECTURE.md) when opening work. Priority order reflects delivery dependencies. Apply P6 tests with the milestone that introduces the behavior.

| Order | Current state | Required change and owners | Dependencies | Acceptance criteria | Risks |
| --- | --- | --- | --- | --- | --- |
| P0. Complete CI/CD and GitOps | P0.1–P0.2 established the docs and contract. P0.3 implements a frozen admission policy, merge guard, publication receipt, read-only preview and local placement checks. History contains a v2 revert with unknown reason. | P0.4, after explicit authorization, verifies hosted read paths and branch protection, then adds and tests App-authored image-only PR writes in an approved lab. | Authorized GitHub and GHCR access, approved lab, App and branch rules, verified deployable baseline, historical revert disposition and digest evidence where available. | An authorized demo traces a source SHA and GHCR digest to one validated config PR, a human merge and observed healthy Argo CD sync. Failed, stale and blocked builds cannot promote. Retry, placement concurrency, rollback and explicit re-promotion are exercised. | Stale refs, racing placement and promotion, unsafe repeat of reverted images, excessive write scope, private or reassigned tags, and merges without required checks. |
| P1. Reproducible infrastructure | Local untracked Terraform and Ansible define a single-AZ EC2/k3s lab. Runtime and reproducibility are unknown. | Platform reviews the draft with its owner, makes Region/AZ and environment consistent, and defines versioned bootstrap, safe state, inventory handoff and cost controls. Config documents authorized Argo CD bootstrap inputs. | P0 deployment contract, approved AWS account and budget, reviewed IaC and environment plan. | Format, validate and syntax checks pass. A reviewed lab plan and repeatable authorized bootstrap yield the expected Ready nodes, private control paths and labels, with documented cost and teardown handling. | Credential or state exposure, public access, drift, single-AZ failure, and surprise cost. |
| P2. Kubernetes reliability and security | Deployment, Service, readiness, requests and non-root policy exist. Hardening and environment patterns are limited. | Config strengthens pod security, rollout/probes, capacity checks, networking and environment/promotion management. Workload owns health semantics and Platform aligns region mapping. | P0 rollback path and P1 lab capacity or an equivalent approved test cluster. | Render and policy tests cover positive and negative cases, approved staging rollout verifies scheduling, least privilege, service access and rollback with the intended labels and capacity. | Unschedulable replicas, overly strict probes and network rules that break required traffic. |
| P3. Observability and SRE | Flask logging and CI failure output exist. Prometheus, Grafana, alerting and service SLOs are planned. | Define signals and SLOs first. Workload and Platform emit useful telemetry. Config owns selected collectors, logging, dashboards and alerts. | Stable environment and readiness behavior from P2, telemetry access and retention constraints. | Service health, latency, error rate and deployment state are visible. A lab failure triggers a tested alert with an owner, a runbook and redacted logs. | High cardinality, noisy pages, sensitive labels and data retention cost. |
| P4. Live placement inputs | Static cost, capacity and RTT with a locally checked ILP and benchmark. | Platform introduces versioned, observable inventory, price and latency inputs with units, age and fallback semantics. Config supplies accurate capacity and label contracts. Workload supplies measured demands where appropriate. | Reproducible cluster, verified schedules and trustworthy inventory or telemetry. | Replayable fixtures prove feasibility and cost invariants. Stale or missing inputs have defined behavior. A lab comparison reconciles candidate placement with schedulable capacity. | Stale metrics, incompatible cost units, solver runtime and misplaced confidence in estimates. |
| P5. Portal deployment controls | Flask form has validation, CSRF and a GitHub PR link. Requester identity, role enforcement, preview and rollout visibility are missing. | Platform adds identity, authoritative authorization, stable sessions, non-mutating deployment preview and audited operations. Config provides review and rollout status. | P0 PR lifecycle, trust design, token and environment scope. Plan access control before any shared exposure. | Identity and role checks are independently tested. Preview does not write, authorized submission produces a traceable request, and UI status reflects PR and rollout evidence. | Unauthorized changes, privilege confusion, duplicates and disclosure in audit logs. |
| P6. Tests, reproducibility and operations docs | CI smoke and config policy exist. Benchmark works on deterministic fixtures. Tracked suites and runbooks are missing. | All repositories add relevant regression and contract tests. Platform maintains benchmark recipes and documentation. Config and Workload add validation and rollback runbooks. | Begin with P0 contract tests and extend each milestone as evidence becomes available. | Unit and integration checks cover failure paths, benchmark inputs and environment are reproducible, and an operator exercises the end-to-end runbook. Portfolio claims link to evidence. | Brittle external tests, noncomparable timing data and stale operational instructions. |

Read the [promotion design and acceptance matrix](IMAGE_PROMOTION.md) and [activation runbook](PROMOTION_RUNBOOK.md). P0.4 requires explicit approval. Complete live baseline inventory and strict config protections before enabling cross-repository automation. Keep digest pinning as a separate Helm contract change.
