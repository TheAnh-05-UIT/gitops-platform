# Workload API image promotion

P0.3 implements local validation and preview. P0.4.1 adds exact-candidate review binding and publication privilege separation. See [ADR 0002](decisions/0002-reviewed-image-promotion.md) for the authentication decision and [project state](PROJECT_STATE.md) for evidence. Hosted enforcement and activation require separate verification.

## P0.3 implementation

- Config owns `promotion/schema.json` and the frozen seed `promotion/workload-api.yaml`. `scripts/promotion_policy.py` enforces structural and transition invariants, including the historical v2 deny entry, one generation increment per control change, explicit re-promotion and a known-history rollback target. A recorded block can gain its previously unknown digest. Its SHA, reason and any established digest are preserved.
- `scripts/check_promotion.py` checks the exact parents of the GitHub proposed merge and loads control and values from the trusted base and candidate Git objects. The trusted `pull_request_target` workflow checks out only protected Config `main` and fetches the synthetic merge as data. The existing PR workflow runs Deployment policy from its separate base checkout. Promotion requires Config origin, the configured bot actor, the active generation and an image-tag-only change. The guard renders the trusted chart with the candidate values.
- `scripts/promote_image.py` offers a fixture-only `dry-run` and a credential-scoped `read-only` preview. The latter reads protected heads, the precise workload attempt, verified receipt archive, GHCR descriptors and existing branch or PR. It rechecks both heads before returning. It classifies a missing, duplicate, stale, closed or partially created proposal. The tool has no branch, commit or PR mutation transport. A stale placement snapshot must refresh from the latest base before any future write.
- Workload `ci.yml` separates build and smoke, Trivy scan and GHCR publication. The scan and publisher use the same immutable artifact ID and verify its archive SHA-256. The publisher verifies the loaded image ID. After push, `scripts/publication_receipt.py` binds the registry manifest digest and image-config digest to the tested handoff and records the scanner version. Same-SHA publishing is serialized and an existing tag stops another push, including when upload of the first receipt failed.
- Workload `promotion-preview.yml` requires explicit opt-in and a pinned Config tool SHA. It uses read-only credentials and has no App token or write command. Historical run `44419195493` predates this receipt and provides no receipt for automatic dispatch.

See the [operational runbook](PROMOTION_RUNBOOK.md) for commands, bootstrap order, permissions and the activation gate.

## Exact candidate approval

The guard reads the open, mergeable PR and protected Config head from GitHub. It compares the received merge object to the API SHA and verifies the two parents in base/head order. It reads intent from the base, checks the image-only change, and renders the trusted chart with candidate values in an environment without API credentials. Candidate workflow code, ordinary comments and PR descriptions grant no approval.

The marker `promotion-approval-sha256:<hex>` hashes canonical JSON containing the Config repository and PR number, base, head, synthetic merge, generation and full intent, workload repository, and rendered image reference. The intent provides source SHA, run and attempt and OCI digest. Only GitHub's `APPROVED` review on that head from an allowlisted independent user can approve that marker. A changed base, head, merge object or intent needs fresh approval. Unresolved mergeability and API or object mismatches fail closed.

The guard independently reads the exact successful workload attempt and latest attempt number, required job and step conclusions, and a checksum-verified, attempt-scoped receipt artifact. Receipts outside the attempt or older than 30 days are rejected. It hashes the raw manifest at the tag and at the digest, verifies the media type and scanned image-config digest, and requires protected workload `main` and fresh source identity. The activation scope is a single-image manifest. OCI indexes require a separately verified platform-aware policy.

| Item | Contract |

| Image | `ghcr.io/theanh-05-uit/gitops-platform-workload-api`, full 40-character lowercase source SHA tag, and independently resolved OCI digest. Treat source commit, workflow run and digest as one candidate. |
| Destination | `TheAnh-05-UIT/gitops-platform-config`, protected `main`, `apps/workload-api/values.yaml`. The writer may change only the single `image.tag` scalar. |
| Workload | Argo CD Application `argocd/workload-api` tracks config `main` and reconciles into namespace `workloads`. The promotion workflow has no cluster credential. |

## Trigger and evidence

1. A successful source `main` build runs HTTP smoke and the image scan, publishes, then reads the exact full-SHA tag from GHCR. In P0.3, capture a publication receipt with workload repository, workflow identifier, run ID, run attempt, source SHA, image repository, media type, manifest or index digest and publication time. Record the digest returned by the push and require the registry resolution to agree. Treat the receipt as data from that exact successful trusted run. If the receipt expires or is missing, require a new verified publication receipt before proceeding.
2. A config owner opens a reviewable admission PR for one exact candidate. Merge it to config `main` with an independent approval. That approval is durable intent, with the expected current image and a generation assigned by config. Publication alone creates no deployment intent.
3. An authorized maintainer starts a separate workload `workflow_dispatch` on protected source `main` with the config request ID. A protected Actions environment can gate release of the App key where available. Otherwise the owner must approve an equivalent protected credential boundary before enabling hosted writes. A repository-scoped key without a trusted execution boundary is insufficient. Automatic proposals triggered after publication can be considered later using the same prerequisite intent and protected checks.
4. The workflow uses trusted code from workload `main`, a fixed allowlist for source, registry, target, branch and path, and strict validation of request data. Read the approved request from live config `main`. Confirm the build run is the designated workflow, event `push` on `main`, successful attempt with confirmed publication, and exactly matches the requested commit and digest. Routine promotion requires the candidate to be the live workload `main` tip. An explicit approved re-promotion may use a verified ancestor under the rules below. A rerun, a tag alone, an OCI label or a PR body is insufficient publication evidence.
5. Independently resolve the SHA tag with the expected OCI or Docker manifest media types, validate the returned digest against the manifest bytes and receipt, and verify that the same manifest is available by digest. For an index, verify the target platform exists and record both index identity and the platform digest needed for runtime checks. Fail closed on missing image, unexpected media type, receipt mismatch, unverified platform or inaccessible evidence.

### Config-owned admission

Proposed control file `promotion/workload-api.yaml` in config, reviewed and guarded on `main`. It holds a monotonically increasing `generation`, `frozen`, a single optional `request` and `blocked_images`. A request contains its ID `workload-api-g<generation>`, mode `promote` or `repromote`, exact workload SHA and OCI digest, trusted workflow run ID and attempt, expected current `repository:tag`, and a reviewable reason or decision link. Retain prior requests in protected Git history. Treat missing, malformed or ambiguous state as a stop.

Only a reviewed config maintainer PR can activate or replace a request, freeze or unfreeze promotion, or add a block. These policy changes increment generation. Keep an append-only history of block entries, each keyed by source SHA and digest when known, with a reason and PR or commit reference. A match on either key blocks routine promotion. Before enabling hosted writes, seed `2dd86b7d8237da0ae37878ae99bc9cf983e3a9d0` with source evidence from `5bcaae9` and `8b5497e`. Its historical digest and revert reason are unknown. Record a digest only when historical evidence establishes it. If handling possible aliases for an unresolved digest cannot be justified, keep writes frozen until the owner decides on the missing evidence and risk.

Remove inherited package write access from repository Actions tokens for this package. Build and scan have `contents: read` only. |
| Workload promotion reader | Workload `GITHUB_TOKEN` with `contents: read` and `actions: read` for source and receipt. For private GHCR, use separate `packages: read` access scoped to the package through GitHub Actions access grants or an approved read identity. Verify availability for the repository and plan. |
| Config PR writer | Dedicated GitHub App installed on the config repository only. Request installation tokens scoped to that repository with `Contents: write`, `Pull requests: write` and implicit `Metadata: read`. Contents write covers bot refs and the values commit. PR write covers listing, creation and closing the App's own superseded proposals. Token permissions do not restrict file paths. Enforce the path and branch controls through protected config checks and rules. |
| Config guard and operators | A required trusted check with read-only access to refs, diffs and publication evidence, called from policy code pinned to a trusted revision. A private registry reader must run with approved isolated access and must only process PR inputs as data. Argo CD uses its separate deployment identity. Humans retain config review and merge permissions. |

Use a short-lived GitHub App installation token minted at job time. Keep its signing key in the approved workload environment, rotate it, and log no token, request headers or raw error bodies. Run trusted pinned Actions and trusted code only in that job. Separate checks, publication and config writes into least-privilege jobs. Avoid secrets in PR-triggered untrusted code. Scope the App out of config and workload `main` bypass lists, workflow changes, Actions administration and cluster access. Where supported, protect the `promotion/workload-api/` branch namespace from other writers. Bind required checks to approved publishers and verify supported plan and rules before enablement. ## PR protocol and races

- Read the current config `main` SHA, values and control from the same revision. Stop if frozen, superseded, blocked or the source is stale. If the exact verified candidate is already the desired image, return a successful no-op. For any other candidate, require the current image to match the request's expected previous image. Treat the same tag resolving to a different digest as an incident.
- Use branch `promotion/workload-api/g<generation>-<full-sha>`, target `main`, and title `chore: promote workload-api <short-sha> (g<generation>)`. PR metadata includes ID, generation, source SHA and workflow attempt URL, image tag and digest, expected previous reference, config base SHA, admission PR link, re-promotion decision when applicable, verification summary and rollback instructions. Metadata is for humans. Validate machine decisions against Git state, candidate commit and verified receipt.
- Query existing PRs by exact origin, branch and base, including closed proposals. A matching open PR is reused or refreshed against the current base. A closed-unmerged PR is terminal for its generation. Across generations, treat a prior closed-unmerged promotion for the same SHA or verified digest as rejected until a reviewed config decision records supersession or explicitly authorizes re-promotion. Resolve its identity from the deterministic head and trusted admission history. Fail closed when the history or identity cannot be verified. A conflicting or foreign head, wrong candidate, or unexpected diff requires human review. Do not reopen rejected PRs on retry.
- Patch the single explicit image tag in the latest trusted values content, preserve comments and line endings, and reject ambiguous layout and duplicate YAML keys. Verify that the full semantic diff changes only `image.tag` and leaves `image.repository`, `replicaCount`, `nodeSelector`, `resources` and all other fields intact. Preserve the portal's values layout. Use immutable blob and commit IDs to construct the diff, create a deterministic bot branch, and update only that branch with a non-force fast-forward from the observed bot head. Recheck control generation, base image, source tip for routine candidates and registry mapping before a ref write and before opening the PR.
- Use one workflow concurrency group per target and `cancel-in-progress: false`. Scheduling order is not a correctness guarantee. The config generation, expected-base image, deterministic identities and strict merge checks enforce ordering across jobs and retries.
- Require existing Helm lint, render and policy checks plus a `promotion-guard` for all config PRs. Evaluate the actual merge candidate against the latest protected config base using trusted policy code. Require the branch to be up to date, stale approvals to be dismissed, an independent human review and human-controlled merge. The guard checks the active generation, blocks, previous value, permitted file diff and publication identity. It rejects changes that combine promotion with unrelated values or weaken controls. Apply the same trust boundary to manual image and policy changes. Reject combined image/control mutations outside the specific reviewed rollback transition.
- At review, recheck the source tip for routine requests and registry tag-to-digest mapping, and reject stale evidence. The config guard protects old runs from superseding a newer approved request through config `main`. A source tip and registry can still change between an external check and Git merge because the three systems have no shared transaction. Require fresh evidence at human merge, keep the same-SHA tag operationally append-only and migrate to digest pinning to eliminate tag pull drift.
- Placement PRs remain separate. If a placement-only PR lands first, reread the latest base, keep the same active request if still valid, and refresh the bot branch without force. Re-run checks and re-review. If promotion lands first, revalidate the placement merge result and confirm that it retains the new image. A conflict, image drift or unrecognized values layout blocks the operation.

### Retries and partial operations

On timeout after a mutation, read the deterministic branch or PR and reconcile before retrying. Recover an App-owned branch without a PR only if its exact candidate, bot history, expected values diff and currently admitted generation still match. A verified branch can be reused to open the missing PR. PR creation races converge by listing the exact head and base again. Stale or orphaned branches are left intact for owner review or closed under an approved cleanup policy.

Use bounded backoff for transient errors and respect `Retry-After` or rate reset headers. Stop on permission denials, rejected tags, invalid schema, mismatches and conflicts. A `409` or `422` must be classified by reading current state, with a fresh attempt only if the same intent and branch ownership remain valid. No error path restores an older value, force-pushes a branch, writes `main`, exposes credentials or applies workloads directly.

## Rollback and explicit re-promotion

1. If operations require rollback, pause dispatch and hold outstanding promotion merges while the rollback PR is reviewed. On the current config base restore only the last known-good image reference, retain current placement, and atomically increment generation, clear the active request, freeze promotion and append a block for the withdrawn SHA and known digest. For a candidate that was rejected before merging, invalidate the request, block the candidate and leave the current image unchanged. The guard applies the block and prior rejection checks to every future promotion merge.
2. Confirm the fallback image is still available and that its descriptor matches the last known-good evidence. If the previous tag no longer matches or cannot be resolved, use an independently verified approved recovery artifact and a reviewed config update. Avoid directly applying workloads. Observe Argo CD sync and health at the rollback commit, Deployment readiness, Pod image identity and service smoke. Escalate if reconciliation or image pull fails.
3. A retried run, open stale PR or prior approval cannot override the new generation or block. To submit the same image again, an authorized owner must explicitly request `repromote` in a new independently reviewed control PR. Record exact SHA and digest, applicable block IDs, evidence addressing the reason for the block or documenting owner disposition of the unknown reason, expected current image, and completed publication and compatibility evidence. If necessary, deliberately unfreeze for that request through the same reviewed change. The block stays in history and the exception applies only to this generation and candidate. An older candidate is allowed only as a reachable ancestor of current protected source `main` under this exception. Normal merge approval and checks still apply. Never infer this exception from a rerun, generic unfreeze or a changed tag.

## Image reference strategy

Keep full source-SHA tags with digest verification to preserve the current chart and portal contracts. A tag is a lookup key, including when it contains a unique commit SHA. The registry can reassign it, and a retry with floating inputs can produce different bytes. Treat first successful publication of a SHA tag as authoritative. The publisher serializes same-SHA attempts and refuses to overwrite an existing tag. The trusted verifier checks the mapping before merge. The current chart leaves image pull policy unspecified. With an ordinary explicit tag, Kubernetes defaults a newly created workload's policy to `IfNotPresent`. A node may use a locally cached tag reference, so verify observed Pod image identities during rollout.

Plan a separate migration to `repository@sha256:...`, which pins exact OCI manifest or index bytes. Introduce an optional validated `image.digest`, preserve tag-only defaults for existing checkouts, and explicitly define digest precedence and rejection of invalid or ambiguous values. First land chart and policy support with compatibility tests. Then migrate the writer and rollback logic, retain known rollback digests and exercise mixed-era configuration and older retained images. Validate registry retention, pull credentials, architecture coverage, Argo CD rollout and Pod runtime identity. This proposal makes no chart change. [Kubernetes image references](https://kubernetes.io/docs/concepts/containers/images/)

## Acceptance matrix

Run pure policy tests and fake GitHub/GHCR integration first. Hosted checks require separate authorization and an approved test target. Identify outcomes with the request ID and redact credentials.

| Scenario | Local unit or integration evidence | Hosted end-to-end evidence |
| --- | --- | --- |
| Successful promotion | Valid run, receipt, digest and fresh approved intent create one image-only PR to `main`. | Capture publisher run, GHCR manifest identity, admission and promotion PRs, required green checks, merge SHA, healthy Argo CD sync and observed workload identity. |
| Failed publication | Failed run or publication job, or absent receipt, stops before writes. | Failed trusted run produces no config proposal. |
| Missing image | Registry `404` or inaccessible descriptor stops before writes. | Try an approved isolated missing-image fixture and confirm no PR. |
| Invalid authentication | `401` and permission `403` stop and return a redacted error. | A revoked or insufficient test installation fails without config mutation. |
| Duplicate requests | Same generation is retried after branch or PR creation, including lost response. Reuse existing branch/PR or return already merged. | Dispatch twice and observe one PR for the request. |
| Existing image reference | Exact matching image and verified digest produce a no-op. Digest mismatch fails. | Re-run a still-valid already-applied intent and confirm no new desired-state change. |
| Concurrent builds | Reorder two completions and simulate overlapping writers. Only current approved generation may propose or merge. | Delay one candidate and approve a newer intent. Older PR is rejected or marked superseded. |
| Stale build | Old run after source advances or expected image changes is rejected. | Show an old generation or outdated source fails with no config overwrite. |
| Previously reverted or rejected image | Seed the historical SHA and known fixture digests. Test retry, alias match and closed unmerged PR. | Demonstrate ordinary retries stay blocked after a lab rollback. |
| Explicit re-promotion | Exact candidate with new approved `repromote` generation can proceed. Reusing an old or partial approval fails. | Independently approve one lab exception and observe one newly reviewed promotion. |
| Concurrent placement PRs | Exercise both merge orders and real conflict. Rechecks use the latest base and retain either PR's disjoint fields. | Merge a placement-only PR while promotion is open. Verify refreshed checks and both desired settings. |
| Preservation of values | Compare parsed values and source diff, including comments, line endings, `replicaCount`, `nodeSelector` and `resources`. | Inspect actual bot PR and rendered manifests for unchanged placement and resources. |
| Config validation failure | Mock policy failure. PR can be investigated and cannot merge. | Required check fails in lab and branch protection blocks merge. |
| Git rollback | Restore verified image and atomically record block and generation. Reject outstanding branch and retry. | Revert through reviewed Git, observe previous image and healthy sync, and prove stale candidates stay blocked. |
| Registry mapping drift | Change a tag mapping between publication and admission, or between proposal and final validation. Fail closed. | With a disposable image, prove mapping mismatch blocks merge verification and preserves desired state. |

## Implementation and activation order

1. For hosted activation, decide the release owner, approved lab, receipt retention, App owner and key boundary, branch rules and merge authority. Use read-only access to verify remote heads, publication history, intended and fallback digests, historical revert disposition and baseline Argo CD state. Keep the historical source SHA blocked even if its digest remains unknown.
2. Bootstrap Config's existing P0.3 files with the historical SHA blocked, then introduce the workflow wiring and verify strict workflow, branch and owner rules on the authorized host.
3. Exercise the implemented Workload receipt and opt-in read-only preview with separate read and publish permissions. Validate the registry, receipt and artifact handling on the hosted runner, including expired artifacts and existing-tag rejection.
4. Run Platform's local cross-repo regressions and hosted placement scenarios with the authorized baseline. Establish reliable evidence for rejection history and digest aliases before enabling any writes.
5. Implement the write adapter with mock tests, then with separately authorized owner actions install the scoped App, set the credential boundary and enable lab PR creation. Verify strict rules and retain a known-good rollback artifact before onboarding the exact lab candidate.
6. Run the hosted acceptance matrix in the authorized lab. Capture one successful PR, blocked stale/retry cases, a reviewed rollback with observed workload evidence and a reviewed explicit lab exception. Leave digest pinning and any wider rollout for their own approved change.
